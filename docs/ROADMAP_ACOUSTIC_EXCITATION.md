# Roadmap: Acoustic Excitation Framework

**Status:** DEFERRED FUTURE CAPABILITY  
**Priority:** High (post-provenance completion)  
**Classification:** INSTRUMENT CLASS: MEASUREMENT  
**Created:** 2026-06-12  
**Blocks:** Controlled acoustic workflows, A0 resonance measurement, transfer-function workflows

---

## Purpose

Introduce controlled acoustic excitation as a governed measurement capability.

The objective is to replace uncontrolled excitation sources (tap events) with known
excitation sources that can participate in workflow provenance, experiment lineage,
repeatability analysis, and transfer-function measurement.

This capability track establishes excitation infrastructure only. It does not
implement modal analysis, recommendations, optimization, or acoustic interpretation.

## DO-90 — Acoustic Excitation Framework Foundation

**Status:** Planned (Post-DO-89)  
**Priority:** High  
**Classification:** INSTRUMENT CLASS: MEASUREMENT

### Scope

#### ExcitationContractV1

Create a canonical excitation contract describing:

| Field | Type | Description |
|-------|------|-------------|
| `excitation_type` | enum | `tone`, `stepped`, `sweep`, `noise`, `impulse` |
| `waveform` | enum | `sine`, `square`, `triangle`, `chirp` |
| `frequency_hz` | float | Fixed frequency (for tone) |
| `start_frequency_hz` | float | Start of range (for stepped/sweep) |
| `stop_frequency_hz` | float | End of range (for stepped/sweep) |
| `duration_s` | float | Duration of excitation |
| `amplitude` | float | Amplitude (0.0-1.0 normalized) |
| `sample_rate` | int | Output sample rate |
| `output_device` | string | Audio output device identifier |

#### KnownToneRecord

Metadata record describing a fixed-frequency excitation event:

| Field | Type | Description |
|-------|------|-------------|
| `tone_id` | string | Unique identifier |
| `frequency_hz` | float | Emitted frequency |
| `duration_s` | float | Emission duration |
| `amplitude` | float | Normalized amplitude |
| `output_device` | string | Device used |
| `emitted_at_utc` | string | ISO 8601 timestamp |
| `epistemic_status` | string | Always `"derived"` |

### Feature A — Fixed Frequency Generator

CLI interface:

```bash
ttp emit-tone --frequency-hz 440
ttp emit-tone --frequency-hz 432
ttp emit-tone --frequency-hz 766
```

Validation:
- frequency > 0
- frequency < Nyquist (sample_rate / 2)
- amplitude within allowed range (0.0-1.0)
- duration > 0

### Feature B — Stepped Excitation

CLI interface:

```bash
ttp emit-steps --start-hz 80 --stop-hz 130 --step-hz 2
```

Purpose:
- Resonance discovery
- A0 measurement
- Modal excitation

### Feature C — Sweep Excitation

CLI interface:

```bash
ttp emit-sweep --start-hz 80 --stop-hz 130 --duration-s 20
```

Purpose:
- Transfer-function measurement
- Resonance discovery
- Workflow-driven acoustic testing

### Provenance Requirements

Every excitation event must be lineage-visible.

Measurements generated using controlled excitation must be able to reference:
- Excitation contract
- Excitation parameters
- Output device
- Excitation type

Questions that must remain answerable:
- Was this measurement generated by tap?
- Was it generated by a tone?
- Was it generated by a sweep?
- Which output device produced the excitation?

### Explicit Non-Goals

Not included in DO-90:
- Modal participation mapping
- Soundhole placement studies
- Acoustic recommendations
- Optimization systems
- AI interpretation
- Build recommendations

### Acceptance Criteria

1. `ExcitationContractV1` dataclass exists in `tap_tone_pi/provenance/`
2. Fixed-frequency tone generation exists (`ttp emit-tone`)
3. Stepped excitation exists (`ttp emit-steps`)
4. Sweep excitation exists (`ttp emit-sweep`)
5. Excitation provenance integrates with `MeasurementLineageV1`
6. Controlled excitation can be invoked by workflows
7. Governance and lineage checks remain green
8. All new code marked `INSTRUMENT CLASS: MEASUREMENT`

## Architectural Notes

### Constitutional Compliance

All excitation systems operate under `INSTRUMENT CLASS: MEASUREMENT`:

- Excitation parameters are **measurement conditions**, not recommendations
- Frequency values are **captured facts**, not quality judgments
- Workflow completion means **procedurally complete**, not successful
- No excitation module may claim advisory authority

### Signal Generator Integration

DO-90 builds on existing `tap_tone_pi/signal_gen/generators.py`:

| Existing | DO-90 Extension |
|----------|-----------------|
| `sine_wave()` | CLI wrapper + provenance |
| `sweep_signal()` | CLI wrapper + provenance |
| `multitone()` | Future stepped excitation |

### Output Device Handling

Excitation output device selection follows calibration patterns:

- Device enumeration via `sounddevice`
- Device ID persisted in excitation records
- Loopback calibration applies to output path
