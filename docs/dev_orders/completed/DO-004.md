## Schema structure

- **wood**: WoodSelection with flitch_id + subid for all components (top, back, sides, neck, braces, fretboard, bridge)
- **as_built_dimensions**: thickness grids, brace dimensions, body measurements
- **measurements**: paths to Phase 2 ods_snapshot, tap-tone, deflection sessions
- **predicted**: T1_hz, A0_hz, T2_hz, T3_hz, bridge_deflection_mm from solver
- **measured_summary**: actual measured values for comparison
- **residuals**: computed prediction errors (hz and pct)
- **subjective**: builder_notes + player_evaluations with ratings

## Key design decisions

**1. Four-stage atomic commits.** Each stage independently mergeable:
- `9737134` Stage A schema
- `ed387d6` Stage B dataclasses
- `98411b6` Stage C CRUD
- `13bbc5f` Stage D cross-reference

**2. Foreign key references.** Wood selection uses flitch_ids that link to
WoodDatabase records from DO-003. BuildDatabase.get_builds_using_flitch()
enables reverse lookups.

**3. Path-based measurement references.** Rather than embedding measurement
data, the schema stores paths to Phase 2 sessions, tap-tone outputs, etc.
This keeps build records small and avoids data duplication.

**4. Automatic residual computation.** compute_and_set_residuals() computes
residuals from predicted and measured_summary, then updates the build record.
Residuals include both absolute (hz) and percentage values.
